# 定子冲片表面缺陷检测系统综合总结

## 1. 文档说明

本文基于以下两份材料整理：

1. 《定子冲片表面缺陷数据预处理及模型开发技术服务项目系统需求说明书》v1.0
2. 《定子冲片表面缺陷检测 Web 可视化系统设计方案》v1.1

需求说明书主要定义系统“要实现什么”和“达到什么标准”，是阶段性验收的重要依据；设计方案进一步说明系统“如何实现”，补充了技术架构、数据库、接口、部署、运维和验收设计。

## 2. 项目背景与建设目标

东方电气定子冲片在冲压、转运和叠片过程中可能产生划痕、点蚀等表面缺陷。现阶段主要依靠人工目检，存在以下问题：

- 人工检测速度约为每分钟 3～4 片，难以匹配产线节拍；
- 检测结果主要通过纸质方式记录，可追溯性较差；
- 检测数据未实现结构化沉淀，难以支撑质量分析和工艺改进；
- 人工判断容易受到疲劳、经验和环境因素影响。

项目拟建设一套支持 7×24 小时运行的定子冲片表面缺陷自动检测系统，实现以下业务闭环：

> 相机拍照 → AI 推理 → 缺陷分类与分级 → PASS/NG 判定 → 数据存储 → Web 实时展示 → MES 上报 → 历史追溯与统计分析

系统应对每张检测图片形成完整记录，包括图片编号、检测时间、操作员、原图、缺陷结果、模型版本、配置版本和 MES 上报状态。

## 3. 系统范围

### 3.1 建设内容

- 工业相机和光源的系统集成；
- AI 模型推理、缺陷分类和等级判断；
- Web 实时检测页面；
- 历史记录、详情查看和数据导出；
- 质量统计分析与车间大屏；
- 缺陷阈值、判定规则、ROI、像素标定等参数配置；
- 用户、日志、文件和 MES 接口管理；
- 系统部署、监控、备份和运维。

### 3.2 系统边界

系统不负责冲压工艺控制、厂级生产调度及定子装配等后续工序。设计方案将相机、光源等设备的底层驱动开发排除在外，计划通过设备适配器进行接入，但该责任边界仍需与客户进一步确认。

## 4. 用户与权限

系统保留两种角色：

| 角色 | 主要职责 |
| --- | --- |
| 管理员 `admin` | 参数配置、用户管理、日志审计、MES 管理、文件策略和系统维护 |
| 操作员 `operator` | 实时检测、历史查询、详情查看、统计分析和数据导出 |

系统采用 RBAC 权限控制。前端根据角色显示菜单和按钮，后端对每个接口执行权限校验。用户连续五次输入错误密码后，账号锁定 30 分钟。

## 5. 核心业务功能

### 5.1 登录与身份认证

- 使用账号和密码登录；
- 密码不少于 8 位，并包含大小写字母、数字和特殊字符；
- 密码采用 bcrypt 加密存储，成本因子为 12；
- 使用 JWT，访问令牌有效期 8 小时，刷新令牌有效期 7 天；
- 支持登录、退出、令牌刷新、账号锁定和相关安全审计；
- 管理员可选择启用 TOTP 双因素认证。

### 5.2 实时检测

实时检测是系统的核心功能，页面主要包括：

1. **图像显示区**：显示当前检测图片，支持缩放、拖动、矩形或多边形缺陷标注；
2. **缺陷信息区**：显示缺陷类型、等级、置信度、像素尺寸和物理尺寸；
3. **产品信息区**：显示图片编号、操作员、检测时间、缺陷数量及 PASS/NG 结果；
4. **设备状态区**：显示相机、PLC、AI 服务、曝光、增益、光源、磁盘和 GPU 状态；
5. **异常告警区**：设备或服务异常时，通过文字、弹窗和 WebSocket 消息进行告警。

实时消息主要分为 `frame`、`infer`、`device` 和 `alert`。客户端断线后采用指数退避策略重连，重连成功后通过实时快照接口恢复最新状态。

### 5.3 历史记录与详情

- 按时间、判定结果、操作员、图片编号和产线筛选；
- 默认按检测时间倒序排列；
- 默认每页 20 条，可切换为 50 或 100 条；
- 查看原图、标注图、缺陷列表和 AI 原始 JSON；
- 查看模型版本、配置版本和配置快照；
- 查看 MES 上报状态、时间、响应码和失败信息；
- 支持导出 Excel、PDF、原图和 JSON；
- 大规模导出通过异步任务执行，避免阻塞请求。

### 5.4 统计分析

统计模块包括：

- 今日检测总数；
- NG 数量；
- 缺陷检出率；
- 划痕与点蚀数量对比；
- 近 7～30 天缺陷率趋势；
- 缺陷类型和等级分布；
- 360° 圆周展开热力图；
- 适用于车间的 1080p 全屏大屏模式。

默认查询最近 7 天的数据并每 60 秒刷新一次，用户可关闭自动刷新。

### 5.5 参数配置

管理员可以配置以下六类参数：

1. 缺陷尺寸阈值；
2. 图片合格判定规则；
3. ROI 检测区域，最多 8 个；
4. 像素与毫米之间的标定比例；
5. 按定子型号管理的相机和光源方案；
6. 模型置信度、NMS 阈值及 CPU/GPU 推理设备。

配置采用“草稿—校验—发布”流程。发布后生成不可变版本号，每次检测绑定当时的配置版本，从而保证历史检测结果能够复现。

### 5.6 系统管理

- 用户增删改、启停和密码重置；
- 操作日志、系统日志和安全事件日志；
- MES 地址、令牌、自动上报开关和连接测试；
- 原图保留期限和磁盘配额；
- 每日定时清理过期文件；
- 审计日志保留 180 天。

## 6. 缺陷分类与判定规则

### 6.1 缺陷分类

当前系统只处理两种缺陷和两个等级：

| 类别 | 系统值 | 显示颜色 |
| --- | --- | --- |
| 划痕 | `scratch` | 橙色 `#FAAD14` |
| 点蚀 | `pitted_surface` | 青色 `#36CFC9` |
| 轻微 | `minor` | 绿色等级标识 |
| 严重 | `severe` | 红色等级标识 |

### 6.2 默认数量规则

| 缺陷类型 | 等级 | 触发 NG 的默认数量 |
| --- | --- | ---: |
| 划痕 | 严重 | ≥ 1 个 |
| 划痕 | 轻微 | ≥ 5 个 |
| 点蚀 | 严重 | ≥ 4 个 |
| 点蚀 | 轻微 | ≥ 9 个 |

设计方案中的判定过程为：

1. 收集当前图片的全部缺陷；
2. 按“缺陷类型 × 缺陷等级”分组统计；
3. 任一启用规则达到规定数量时判定为 NG；
4. 否则，如果存在严重缺陷，则判定为 NG；
5. 其他情况判定为 PASS。

## 7. 技术架构

### 7.1 推荐技术栈

| 层次 | 技术方案 |
| --- | --- |
| 前端 | Vue 3、TypeScript、Vite、Element Plus、ECharts、Fabric.js、Pinia、Axios |
| 后端 | FastAPI、Pydantic v2、SQLAlchemy 2.x Async、Alembic |
| 数据库 | MySQL 8.0 InnoDB |
| 缓存与消息 | Redis 7.x |
| 异步任务 | Celery + Redis |
| 文件存储 | MinIO 或本地 NAS |
| 报表 | openpyxl、WeasyPrint |
| 部署 | Docker、Docker Compose，后续可扩展至 Kubernetes |
| 监控 | Prometheus、Grafana、结构化 JSON 日志 |

### 7.2 服务划分

- `web-api`：认证、权限、查询、统计、配置、审计和导出任务；
- `realtime-gateway`：维护 WebSocket 连接并推送实时消息；
- `inference-service`：监控图片目录并执行 AI 推理；
- `decision-service`：根据配置版本完成 PASS/NG 判定；
- `mes-adapter`：异步上报 MES，负责重试、幂等和人工补报；
- `worker/maintenance`：导出、统计汇总、文件清理和备份检查。

FastAPI 不直接承担图像推理和大文件传输。推理、文件、实时网关与 Web API 相互隔离，避免推理或文件处理阻塞用户请求。

### 7.3 图片处理流程

工业相机将图片保存到共享文件夹，推理服务通过 `watchdog` 监控新文件。检测完成后，结果写入数据库，原图移动到归档目录，再通过 WebSocket 推送结果并异步上报 MES。

文件夹按照日期分级存储，以避免单目录文件过多。推理服务异常重启后，可以继续处理尚未完成的图片。

## 8. 数据库与接口设计

### 8.1 主要数据表

- 用户和刷新令牌表；
- 检测记录主表；
- 检测文件表；
- 缺陷明细表；
- 设备状态表；
- 告警表；
- 配置版本表；
- MES 上报记录表；
- 审计日志表。

检测主记录、缺陷明细和文件元数据应在同一事务中写入。MES 上报与检测结果解耦，上报失败不能回滚检测结果。

### 8.2 接口设计原则

- REST API 统一使用 `/api/v1` 前缀；
- JSON 字段采用 `snake_case`；
- 时间采用带时区的 ISO 8601 格式；
- 统一返回错误码、错误消息、详情和 `trace_id`；
- 配置发布、MES 上报和导出任务等写接口使用幂等键；
- 文件通过短时签名 URL 下载，API 不直接传输大文件；
- 历史记录必须使用服务端分页。

### 8.3 WebSocket 设计

WebSocket 使用 WSS，并通过令牌认证。消息包含事件 ID、序号和发生时间，用于去重、排序和问题追踪。

消息优先级为：

1. `ERROR`、`ALERT`：立即推送；
2. `DEVICE`、`INFER`：正常队列推送；
3. `FRAME`：网络状况较差时允许降级或丢弃。

## 9. 性能、可靠性与安全要求

### 9.1 性能指标

| 指标 | 目标值 |
| --- | ---: |
| 单张推理耗时 | ≤ 5 秒 |
| WebSocket 端到端延迟 | ≤ 200 ms |
| HTTP API P95 响应时间 | ≤ 300 ms |
| 实时页面渲染速度 | ≥ 24 FPS |
| 10 万条历史记录查询 | ≤ 1 秒 |
| 并发用户数 | ≥ 50 |

需求说明书还提出：1 mm 以上缺陷的漏检率不超过 0.5%，误判为 NG 的比例不超过 3%。

### 9.2 可靠性指标

| 指标 | 目标值 |
| --- | ---: |
| 月度非计划停机 | ≤ 0.5% |
| RTO | ≤ 30 分钟 |
| RPO | ≤ 5 分钟 |
| 关键服务单点故障 | 0 |

设计方案建议 Web API 和实时网关采用双副本，通过 Nginx 负载均衡，并提供存活检查、就绪检查、故障摘除和优雅停机机制。

### 9.3 安全要求

- 全站使用 HTTPS，WebSocket 使用 WSS，TLS 版本不低于 1.2；
- 数据库、MES 令牌和 JWT 密钥不得写入代码仓库；
- 使用 ORM 和参数化查询防止 SQL 注入；
- Vue 默认转义，富文本使用白名单过滤；
- 后端逐接口执行权限校验；
- 敏感写操作需要二次确认；
- 审计日志只允许追加，禁止普通用户修改和删除；
- 所有业务数据存储在客户内网，不出厂。

## 10. 部署与实施计划

### 10.1 首期部署

首期建议使用工业服务器和 Docker Compose，部署内容包括：

- Nginx；
- Vue 静态站点；
- 两个 FastAPI 实例；
- 两个 WebSocket 网关实例；
- GPU 推理服务；
- Celery Worker；
- Redis、MySQL、MinIO；
- Prometheus 和 Grafana。

推荐硬件配置为 8 核 16 线程以上 CPU、64 GB 内存、RTX 3060 12 GB 以上 GPU、500 GB 系统盘和 2 TB 数据盘或 NAS。

### 10.2 实施阶段

| 阶段 | 主要任务 | 预计工期 |
| --- | --- | ---: |
| 阶段 1 | 基础工程、数据库、认证、权限、日志和监控骨架 | 2 周 |
| 阶段 2 | 设备适配、推理、判定、落库和实时页面 | 3 周 |
| 阶段 3 | 历史记录、文件下载和异步导出 | 2 周 |
| 阶段 4 | 统计、六类配置、版本管理和审计 | 3 周 |
| 阶段 5 | MES、压测、故障演练和验收文档 | 2 周 |

需求说明书中的计划节点为：2026 年 10 月完成 PoC 联调，11 月进行单产线试运行，12 月完成验收交付。

## 12. 需要优先统一和确认的问题

### 12.1 API 路径不统一

接口总表使用 `/detections`、`/exports`、`/configs/{type}`，详细接口则使用 `/history/records`、`/history/export`、`/config/current` 等路径。开发前必须确定唯一的接口命名规范。

### 12.2 判定边界存在歧义

材料中同时出现“超过上限判 NG”和“达到上限即 NG”。应明确采用 `count >= max_count` 还是 `count > max_count`，并同步修改需求、接口说明和测试用例。

### 12.3 缺陷名称不统一

文档中混用了“点蚀”“麻点腐蚀”“腐蚀”和 `defect-stain`。建议统一中文名称、接口枚举、数据库值和前端变量。

### 12.4 结果枚举不统一

判定函数使用 `ok/ng`，接口和页面使用 `PASS/NG`。应明确系统内部与外部接口的标准枚举及映射关系。

### 12.5 告警等级不统一

功能章节只定义 `warning/error`，WebSocket 详细协议又定义 `info/warning/error/critical`。需要统一等级、颜色、触发条件和处理策略。

### 12.6 硬件责任边界不清晰

需求包含相机和光源硬件集成，设计方案却排除了底层驱动开发。应明确相机、PLC、光源驱动、设备适配器和现场联调分别由哪一方负责。

### 12.7 AI 模型验收设计不足

需求提出漏检率和误检率指标，但设计方案的验收章节主要关注 Web 功能和系统性能，缺少以下内容：

- 数据采集和标注规范；
- 训练集、验证集和测试集划分；
- 1 mm 缺陷的测量与判定方法；
- 漏检率和误检率计算口径；
- 样本量、现场复测和模型版本冻结机制。

### 12.8 高可用目标与首期部署可能冲突

文档要求关键服务无单点故障，但首期 Docker Compose 方案中的 MySQL、Redis 和 MinIO 可能仍是单实例。应明确首期验收是否要求数据库、缓存和存储也具备高可用能力。

### 12.9 数据保留期限尚未冻结

需求底线为至少保留 3 周，文件策略默认 90 天，设计方案也把存储容量列为待确认事项。应根据每日图片数量、平均图片大小和存储预算计算最终保留期限。

### 12.10 实时频率表述不一致

部分章节规定 `frame` 每 1.5 秒、`infer` 每 1.7 秒、`device` 每 2 秒推送，另有章节标题写“每秒 1 次”。应明确每种消息的实际频率和允许波动范围。

### 12.11 登录令牌存储策略需要统一

需求说明书写明令牌存入 `localStorage`，安全章节又提到 SameSite Cookie。应明确访问令牌和刷新令牌的实际存储位置、刷新机制、退出吊销和 CSRF 防护方案。

## 13. 综合结论

本项目是一套以 AI 表面缺陷检测为核心、以 Web 平台完成实时监控、质量追溯、参数配置、统计分析和 MES 对接的工业质检系统。

现有需求说明书已经基本覆盖业务范围、用户角色、核心功能和非功能指标；Web 设计方案进一步细化了技术栈、服务拆分、数据库、API、WebSocket、部署和运维方案，整体已具备进入详细设计和开发阶段的基础。

正式开发前，应优先冻结接口路径、判定边界、缺陷与结果枚举、告警等级、硬件责任范围和 AI 模型验收方法，并建立“需求编号—设计章节—接口—测试用例”的追踪矩阵，以减少开发返工和验收争议。
