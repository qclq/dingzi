# 开放问题与文档冲突

> 本文件只记录冲突、歧义和设计缺口，不代表已经批准任何建议。  
> 当前共 **28 项登记问题**：其中 Q004、Q006、Q007 已裁决，剩余 **25 项待确认**。所有未标记为“已裁决”的项，在权责方书面确认前均不得由开发人员自行裁决。阶段内已授权的常规技术实现不因此额外要求审批。

## 文档适用顺序（项目负责人已确认）

1. 《定子冲片表面缺陷数据预处理及模型开发技术服务项目系统需求说明书》为根本依据：用于裁决需求范围、业务语义、验收标准及与其他文档的冲突。
2. 《定子冲片表面缺陷检测Web可视化系统设计方案V1.1》为额外依据：仅在不与需求说明书冲突时，用于补充接口、数据模型、交互和实现细节。
3. 后续所有阶段均遵循上述顺序；设计方案与需求说明书冲突时，必须以需求说明书为准，并在本文件记录实现映射或仍待确认的缺口。

## Q001

类型：明确冲突（历史接口路径）

需求说明书：
历史记录、详情和下载功能必须实现，但未规定 REST 路径。

设计方案：
接口总表使用 `GET /api/v1/detections`、`GET /api/v1/detections/{id}`、`GET /api/v1/detections/{id}/files/{kind}`；详细章节改为 `GET /api/v1/history/records` 和 `GET /api/v1/history/records/{record_id}`。

冲突：
同一资源存在两套正式路径与资源命名，前后端无法据此形成唯一契约。

建议处理：
优先采用资源式 `/api/v1/detections` 体系，或由项目负责人书面选择另一套；冻结后同步 OpenAPI、追踪矩阵和测试。

## Q002

类型：明确冲突（导出接口路径）

需求说明书：
要求 Excel/PDF 异步导出和任务状态查询。

设计方案：
接口总表为 `POST /api/v1/exports`、`GET /api/v1/exports/{id}`；详细章节为 `POST /api/v1/history/export/excel`、`GET /api/v1/history/export/tasks/{task_id}`。

冲突：
创建和查询任务均有两套路径，PDF 导出路径也未定义。

建议处理：
冻结统一异步任务资源模型，并补充 Excel/PDF 的 `type`、筛选快照、状态、进度、错误和签名 URL 字段。

## Q003

类型：明确冲突（统计接口路径与覆盖范围）

需求说明书：
要求概览、日/周/月柱状图、7～30 天趋势、360°热力图和类型×等级饼图。

设计方案：
总表定义 `/analytics/overview`、`/analytics/trends`、`/analytics/heatmap`；详细章节定义 `/analytics/overview`、`/analytics/defect-trend`、`/analytics/defect-distribution`，未给出热力图详细结构。

冲突：
趋势路径不一致，热力图缺少详细契约，分布接口未出现在总表。

建议处理：
冻结一套统计 API，并补齐聚合粒度、指标口径、热力图坐标和空数据行为。

本轮 Phase 5 实施决策（2026-09-03，待正式需求变更单归档）：保留
`/analytics/overview`、`/analytics/trends`、`/analytics/heatmap`，同时提供设计详细章节中的
`/analytics/defect-trend`（兼容趋势路径）和 `/analytics/defect-distribution`。缺陷检出率统一为
`NG 检测记录数 / 检测总数 × 100`，无检测记录时返回 `0.00`；热力图采用归一化 bbox 中心点的临时
映射，响应中明确 `coordinate_basis=normalized_bbox_center`，不宣称其为相机物理角度标定。

## Q004

类型：明确冲突（配置接口与生命周期）

需求说明书：
六类配置需恢复默认、保存、启停，并支持持久化。

设计方案：
总表使用 `GET/PUT /api/v1/configs/{type}`；详细章节使用 `GET /api/v1/config/current`、`POST /api/v1/config/update`、`GET /api/v1/config/versions`，功能章节又规定“草稿—校验—发布”。

冲突：
路径、HTTP 方法、按类型或整体提交以及草稿/发布语义不一致。

建议处理：
定义配置资源、草稿校验、发布、回滚、恢复默认和版本查询的完整状态机及 API。

状态：已裁决（项目负责人，2026-09-03）

裁决依据与实现映射：

- 附件 1 只规定配置功能和 `/config` 页面，不规定 REST 路径；因此可使用附件 2 中不冲突的资源式路径作为补充。
- 以 `GET/PUT /api/v1/configs/{type}` 管理六类配置的草稿；不采用附件 2 详细章节中相互冲突的旧 `/api/v1/config/*` 路径。
- 发布状态机统一为 `POST /api/v1/configs/validate`、`POST /api/v1/configs/publish`、`GET /api/v1/configs/versions` 和 `GET /api/v1/configs/versions/{config_version}`。发布的是完整配置包，生成一个不可变 `config_version`；检测记录绑定该版本及快照。

## Q005

类型：明确冲突（PASS/NG 数量边界）

需求说明书：
算法文字写“任一启用规则超出 `maxCount` → NG”，默认规则表却写“≥1/5/4/9 个触发 NG”。

设计方案：
判定步骤明确 `count >= maxCount`，另有页面说明“超出上限即 NG”。

冲突：
无法确定边界应为 `>=` 还是 `>`，会直接改变验收结果。

建议处理：
建议采用与默认表一致的 `count >= max_count`；必须经需求方书面确认并形成边界测试。

## Q006

类型：明确冲突（缺陷分级阈值结构）

需求说明书：
每类缺陷以单一阈值区分“轻微 ≤ 阈值 / 严重 > 阈值”。

设计方案：
配置 API 同时定义 `minor_threshold_mm` 和 `severe_threshold_mm` 两个阈值。

冲突：
单阈值和双阈值模型不同；双阈值可能产生空档或重叠区间。

建议处理：
确认采用单一 `severity_threshold_mm`，或明确双阈值之间的等级及边界规则。

状态：已裁决（项目负责人，2026-09-03）

裁决依据与实现映射：

- 附件 1 的 `FR-CFG-T02` 明确“轻微 ≤ / 严重 >”，优先于附件 2 的 `minor_threshold_mm` 和 `severe_threshold_mm` 双字段示例。
- 每个缺陷类型保存一个 `severity_threshold_mm`（`0.00`～`100.00` mm，最多两位小数）；前端仍按“轻微”“严重”两行展示同一分界值及其包含/排除关系，不创建空档或重叠区间。
- 附件 1 要求的行级启用/停用按“类型 × 等级”保存；关闭某等级时，该等级不参与阈值分级。发布校验要求每种缺陷至少启用一个等级。

## Q007

类型：歧义（用于分级的尺寸维度）

需求说明书：
写明“不同长度阈值对应不同等级”。

设计方案：
缺陷同时包含 `width`、`height`、`area`，未规定使用宽、高、最大边、长轴还是面积进行分级。

冲突：
同一缺陷可能因选用尺寸维度不同得到不同等级。

建议处理：
按缺陷类型分别定义测量维度、单位、取整方式、标定误差和边界比较方法。

状态：已裁决（项目负责人，2026-09-03）

裁决依据与实现映射：

- 附件 1 将分级依据定义为“长度”；附件 2 仅补充检测结果已有 `width_mm` 和 `height_mm`，未指定另一种覆盖性语义。
- 统一以 `max(width_mm, height_mm)` 作为缺陷长度（mm）参与阈值分级；缺少任一物理尺寸时不重新分级，保留模型返回的等级并在原始结果中保留缺失信息。
- 物理尺寸由已发布版本的 `mm_per_pixel` 换算，阈值比较不在历史检测上重算。

## Q008

类型：明确冲突（缺陷名称与变量）

需求说明书：
正式类型为“点蚀”/`pitted_surface`，颜色变量却写成 `--defect-stain`。

设计方案：
在“点蚀”“麻点腐蚀”“腐蚀”之间混用，枚举仍为 `pitted_surface`。

冲突：
中文术语和前端变量不统一，可能导致接口、数据库、图例和验收用语分裂。

建议处理：

## Q009

类型：明确冲突（判定结果枚举）

需求说明书：
算法内部 `totalResult ∈ {ok, ng}`，页面要求 PASS/NG。

设计方案：
REST、WebSocket 和页面示例使用 `PASS | NG`，数据库字段未规定枚举值。

冲突：
内部、接口和数据库标准值未冻结。

建议处理：
建议全链路统一 `PASS | NG`；若内部保留 `ok/ng`，必须定义唯一映射层且禁止泄漏到 API。

## Q010

类型：明确冲突（告警等级枚举）

需求说明书：
FR-RT-08 只定义 `warning | error`。

设计方案：
功能章节仍写 `warning | error`，WebSocket 详细协议扩展为 `info | warning | error | critical`。

冲突：
前端颜色、过滤、外部推送和验收无法使用统一等级。

建议处理：
由需求方确认二级或四级模型，并同步数据库、WS、日志和测试。

## Q011

类型：明确冲突（ALERT 字段）

需求说明书：
告警需要异常类型、首次发生时间、建议处理，概要字段为 `level/type/first_seen_at/device_id`。

设计方案：
WS 概要表同样使用 `level/type/first_seen_at/device_id`；详细协议改为 `severity/category/first_occurred_at/line_id/related_component`。

冲突：
同一消息的字段名和设备/产线关联方式不同。

建议处理：
冻结 ALERT JSON Schema 和兼容策略，不得由前端同时猜测两套字段。

## Q012

类型：明确冲突（DEVICE 指标）

需求说明书：
要求相机连接、曝光、增益、光源亮度、磁盘剩余、GPU 利用率及阈值。

设计方案：
功能表包含这些指标；REST `/device/status` 和详细 WS DEVICE 却主要返回 PLC、AI、存储、磁盘使用率和内存使用率，缺少曝光、增益、光源和 GPU。

冲突：
后端契约不能满足正式设备状态面板。

建议处理：
补齐统一设备状态 Schema、采样频率、单位、基准值、阈值和告警持续时间。

## Q013

类型：明确冲突（WebSocket 时间频率）

需求说明书：
表格为 frame 1.5s、infer 1.7s、device 2.0s；第 10.2 节标题写“每秒 1 次”。

设计方案：
延续 1.5s/1.7s/2.0s，但 DEVICE 详细说明又称“状态变化时推送”。

冲突：
周期推送、变化推送和每秒一次三种语义并存。

建议处理：
为每种消息定义触发方式、目标间隔、允许抖动和空闲心跳；DEVICE 可采用周期快照加变化事件但需明确。

## Q014

类型：明确冲突（图片编号交互）

需求说明书：
FR-RT-02 明确“图片编号输入框”。

设计方案：
实时页面写“显示当前检测图片的唯一编号”，FRAME 消息由服务端提供 `image_id`，未定义用户输入或提交接口。

冲突：
图片编号是人工输入还是设备自动生成未确定。

建议处理：
确认编号生成方、编辑时机、唯一性、校验、与文件名/MES 的关联以及修改审计。

## Q015

类型：明确冲突（Token 存储与 CSRF）

需求说明书：
FR-AUTH-03 要求 token 存入 `localStorage`；安全章节又写 SameSite Cookie + Token 校验。

设计方案：
沿用 Axios 注入 Authorization，同时写 SameSite Cookie 防 CSRF，未区分 access/refresh token 的存储位置。

冲突：
浏览器令牌存储、刷新和 CSRF 模型不完整且可能互斥。

建议处理：
冻结 access/refresh 的存储、轮换、吊销和退出策略；若改变 `localStorage` 要走需求变更流程。

## Q016

类型：明确冲突（密码重置交付物）

需求说明书：
FR-SYS-U04 写“重置密码（发送至预留邮箱）”。

设计方案：
写“发送重置链接至预留邮箱”，但用户字段和 API 未定义邮箱、重置令牌或 SMTP 流程。

冲突：
发送新密码还是一次性重置链接不一致。

建议处理：
出于安全建议采用一次性重置链接，补齐邮箱、令牌过期、单次使用和审计要求，并由需求方批准。

## Q017

类型：明确冲突（用户字段与管理 API）

需求说明书：
用户列表必须含账号、姓名、角色、状态、最后登录，并支持增删改、启停和密码重置。

设计方案：
用户 API 响应缺少姓名/邮箱；创建接口也缺少姓名/邮箱；仅详细定义列表、创建、更新，未定义删除、独立启停、解锁和重置接口。

冲突：
API 无法完整实现 FR-SYS-U01、U02、U04。

建议处理：
冻结用户实体字段和完整管理 API，明确删除采用软删除。

## Q018

类型：明确冲突（日志保留期限）

需求说明书：
FR-SYS-L05 写日志保留 180 天。

设计方案：
将操作日志设为 180 天、系统日志设为 90 天。

冲突：
系统日志是否允许只保留 90 天未获需求依据。

建议处理：

## Q019

类型：明确冲突（高可用与首期部署）

需求说明书：
单点故障目标为 0，关键服务均双副本。

设计方案：
首期仅明确 FastAPI×2 和 WebSocket 网关×2；MySQL、Redis、MinIO、Celery、推理服务和 Nginx 均可能为单实例。

冲突：
首期 Docker Compose 拓扑不能证明“关键服务无单点故障”。

建议处理：
定义关键服务清单和首期验收豁免，或为数据库、缓存、存储、代理和任务系统补齐 HA。

## Q020

类型：缺口（AI 模型验收）

需求说明书：
要求 1 mm 以上缺陷漏检率 ≤0.5%、误判 NG 比例 ≤3%。

设计方案：
验收章节没有定义数据集、样本量、标注规则、划分方法、置信区间、1 mm 测量方法和模型冻结版本。

冲突：
指标存在但无法形成可重复的验收测试。

建议处理：
补充独立 AI 验收方案和固定测试集，由双方签字后执行。

## Q021

类型：歧义（硬件责任边界）

需求说明书：
项目范围包含工业相机和光源硬件集成。

设计方案：
系统边界排除底层驱动开发，声明通过适配器接入。

冲突：
驱动、适配器、PLC 触发、现场调试和故障支持的交付责任不清晰。

建议处理：
建立 RACI，明确客户、硬件供应商和软件方的责任及验收接口。

## Q022

类型：明确冲突（像素标定方向）

需求说明书：
FR-CFG-CA01 定义“1 像素 = N mm”。

设计方案：
配置 API 使用 `pixels_per_mm`（每毫米像素数）。

冲突：
两者互为倒数，直接复用会造成物理尺寸计算错误。

建议处理：
建议使用语义明确的 `mm_per_pixel` 与需求一致，并定义精度和零值校验；如保留 `pixels_per_mm`，必须正式变更需求和映射。

## Q023

类型：歧义（检测时间语义）

需求说明书：
页面和导出统一称“检测时间”。

设计方案：
数据库使用 `detected_at`，REST/WS 多处使用 `captured_at`，另有推理完成时间但字段未独立定义。

冲突：
筛选、排序、报表和性能测量可能使用不同时间点。

建议处理：
分别定义 `captured_at`、`inference_started_at`、`inference_completed_at`、`decided_at`，并指定 UI“检测时间”的正式映射。

## Q024

类型：缺口（FR 编号断档）

需求说明书：
实时模块包含 FR-RT-01～04 和 FR-RT-06～10，没有 FR-RT-05。

设计方案：
章节声称覆盖 FR-RT-01～FR-RT-10，未说明 RT-05 内容。

冲突：
无法判断 RT-05 是误删、保留编号还是设备状态面板对应的遗漏需求。

建议处理：
由需求负责人确认；在正式补发前追踪矩阵不得虚构 FR-RT-05。

## Q025

类型：歧义（数据保留与容量）

需求说明书：
目标表把“数据保留年限”写为“≥3 周”，文件策略默认原图 90 天。

设计方案：
沿用至少 3 周和建议 90 天，并把实际容量列为待确认事项。

冲突：
“年限”字段名称明显不匹配单位，且检测元数据、原图、结果图、报告、日志的保留期限未分别冻结。

建议处理：
基于日图片量、平均文件大小和存储预算形成容量模型，分别冻结各类数据期限。

## Q026

类型：缺口（外部告警接口）

需求说明书：
FR-RT-10 要求告警信息推送到外部系统。

设计方案：
仅描述可推送 MES 或外部系统，并把钉钉/企微/邮件列为待确认；未定义目标系统、字段、鉴权、重试、幂等和失败处理。

冲突：
无法实现或验收外部告警推送。

建议处理：
确认目标渠道并补充独立协议；不要默认把质量结果 MES 上报等同于告警推送。

## Q027
